Pergunta central do usuário: “dá pra conciliar a RLS atual com as boas práticas?”

Resposta direta: SIM, dá pra conciliar — mas é delicado

O modelo de acesso do app (papel em profiles.role + hierarquia user_access por espaço/pasta + visibilidade por responsável/observador/criador) mapeia limpo para RLS real. E não é teórico: já existe precedente no próprio banco — teams/team_members restringem escrita por papel (ADMIN/GESTOR) e task_watchers restringe por auth.uid(). Dá para estender esse mesmo padrão ao núcleo.

Por que é delicado: a RLS precisa espelhar exatamente os filtros que hoje vivem só no cliente (inclusive “Minhas Tarefas”, Caixa de Entrada e tarefas atribuídas fora dos espaços concedidos). Uma política estrita demais faz o usuário “perder” dados e o app quebra; frouxa demais não resolve o vazamento. Além disso, faltam índices na cadeia hierárquica, sem os quais a RLS fica lenta. Por isso a recomendação é fazer em branch do Supabase, validar com o E2E, e só então promover — nunca direto na produção.

Estado atual (evidência)

RLS está habilitada nas 37 tabelas — mas na maioria com política decorativa (USING true para authenticated), o que equivale a “sem restrição”. O controle real acontece só no cliente (filtros de userAccess em React), então qualquer usuário autenticado pode ler/escrever tudo via API REST e via Realtime.

  • Hierarquia: tasks.list_id → lists.folder_id → folders.space_id. Tarefa também tem main_assignee_id, secondary_assignee_ids[], created_by, project_id.

Como conciliar — desenho da RLS (proposta, NÃO aplicada)

1) Funções auxiliares SECURITY DEFINER (evitam recursão de RLS e centralizam a regra)

-- STABLE + search_path fixo; SECURITY DEFINER para ler user_access/profiles sem cair na própria RLS
create or replace function public.is_admin() returns boolean
  language sql stable security definer set search_path = public as $$
  select exists(select 1 from profiles where id = auth.uid() and role = 'ADMIN')$$;

create or replace function public.can_access_space(p_space uuid) returns boolean
  language sql stable security definer set search_path = public as $$
  select public.is_admin() or exists(
    select 1 from user_access ua where ua.user_id = auth.uid() and p_space = any(ua.space_ids))$$;

create or replace function public.can_access_folder(p_folder uuid) returns boolean
  language sql stable security definer set search_path = public as $$
  select public.is_admin()
    or exists(select 1 from user_access ua where ua.user_id = auth.uid() and p_folder = any(ua.folder_ids))
    or exists(select 1 from folders f where f.id = p_folder and public.can_access_space(f.space_id))$$;

create or replace function public.can_access_list(p_list uuid) returns boolean
  language sql stable security definer set search_path = public as $$
  select exists(select 1 from lists l where l.id = p_list and public.can_access_folder(l.folder_id))$$;

-- Tarefa: acessível se a lista é acessível OU o usuário é responsável/criador/observador
create or replace function public.can_access_task(p_task uuid) returns boolean
  language sql stable security definer set search_path = public as $$
  select exists(select 1 from tasks t where t.id = p_task and (
      public.can_access_list(t.list_id)
      or t.main_assignee_id = auth.uid()
      or auth.uid() = any(t.secondary_assignee_ids)
      or t.created_by = auth.uid()
      or exists(select 1 from task_watchers w where w.task_id = t.id and w.user_id = auth.uid())))$$;

2) Políticas (exemplos) substituindo USing true

-- user_access: cada um lê o próprio; só ADMIN escreve
drop policy auth_user_access on user_access;
create policy ua_select on user_access for select to authenticated
  using (user_id = auth.uid() or public.is_admin());
create policy ua_write on user_access for all to authenticated
  using (public.is_admin()) with check (public.is_admin());

-- spaces / folders / lists / tasks: pela hierarquia
create policy spaces_sel on spaces for select to authenticated using (public.can_access_space(id));
create policy tasks_sel  on tasks  for select to authenticated using (public.can_access_task(id));
create policy tasks_ins  on tasks  for insert to authenticated with check (public.can_access_list(list_id));
create policy tasks_upd  on tasks  for update to authenticated using (public.can_access_task(id));

-- profiles: leitura geral (diretório de menções) ok; update só do próprio, role só ADMIN
create policy prof_upd on profiles for update to authenticated
  using (id = auth.uid() or public.is_admin());

3) Índices de suporte (sem eles a RLS fica lenta)

create index on tasks(list_id);
create index on lists(folder_id);
create index on folders(space_id);
create index on tasks(main_assignee_id);
create index on tasks(created_by);
create index on user_access using gin(space_ids);
create index on user_access using gin(folder_ids);

Riscos da mudança e mitigação

  • Quebrar visibilidade legítima (Minhas Tarefas / Inbox / tarefas atribuídas fora do espaço): as políticas incluem responsável/criador/observador em can_access_task. Precisa mapear todos os filtros do cliente antes de fechar.
  • Escritas do app: automações inserem tarefas com created_by = actor (ok com can_access_list); Edge Functions usam service_role (bypassa RLS — ok). Revisar cada WITH CHECK contra os caminhos reais de escrita.
  • Performance: funções STABLE + índices acima; usar (select auth.uid()) para caching por statement.
  • Realtime: a RLS passa a valer para o Realtime (é o que fecha o vazamento), mas confirmar que os canais do app continuam recebendo o que precisam.
  • Rollout seguro: aplicar numa branch do Supabase (MCP create_branch), rodar o E2E (smoke-auth + task-creation-access + visibility-realtime-admin) e um smoke manual por papel; só então merge_branch. Manter migrations reversíveis.

Plano de rollout sugerido (faseado, reversível)

  1. Fase 0 — índices (achado #5): seguro, melhora perf já, e prepara o terreno. Migration isolada.
  2. Fase 1 — raiz da confiança: fechar user_access (#1) e profiles UPDATE (#3) + revisar RPCs SECURITY DEFINER (#4). Baixo tráfego, alto ganho.
  3. Fase 2 — helpers + hierarquia: criar as funções e trocar as políticas de spaces/folders/lists/tasks e sub-entidades (#2), tudo em branch, validado por E2E.
  4. Fase 3 — limpeza: remover políticas duplicadas (#6), fixar search_path (#7), ligar proteção de senha (#8).

Esforço total estimado: 2–4 dias de trabalho cuidadoso (a maior parte é mapear os filtros do cliente e validar, não escrever SQL).

Conclusão

Conciliável: sim. A arquitetura de permissões do app é expressável em RLS, com precedente já no banco. O trabalho real não é o SQL — é espelhar fielmente os filtros do cliente (papéis + user_access + responsável/observador/criador), adicionar índices e validar em branch com o E2E antes de promover. Recomendo começar pela Fase 0 (índices) e Fase 1 (fechar user_access e profiles) — maior redução de risco com menor chance de quebra — e deixar a Fase 2 (núcleo) para uma janela dedicada com validação por papel.

Conforme o playbook, esta análise não alterou nenhum objeto do banco, política ou dado. Todos os comandos SQL acima são propostas.
